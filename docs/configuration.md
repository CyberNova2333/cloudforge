# Configuration

CloudForge reads its configuration from `wrangler.jsonc` (generated from [`wrangler.jsonc.example`](../wrangler.jsonc.example) by `yarn cloudforge install`, or copied from it by hand; gitignored) and from Worker secrets. **Site admin → Setup** checks the installation prerequisites on the running worker (secrets, bindings, variables, migrations, AI Gateway) and shows how to fix what's wrong. Optional OIDC linking has a separate administrator preview/publication step described below; a healthy Setup page does not mean an OIDC provider is published.

## Bindings

Binding names are load-bearing — the worker looks them up by exact name. Resource names and IDs can be anything.

| Key                               | Required value       | What it is                                                                                                                                                                                                                                                                                                                                                                                         |
| --------------------------------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `d1_databases[].binding`          | `"DB"`               | Users, invitations, tokens, repositories, pull requests, comments                                                                                                                                                                                                                                                                                                                                  |
| `artifacts[].binding`             | `"ARTIFACTS"`        | Git storage. `namespace` groups this instance's repositories                                                                                                                                                                                                                                                                                                                                       |
| `send_email[].name`               | `"EMAIL"`            | Outbound invitation, email-verification and password-reset mail via Cloudflare Email Sending                                                                                                                                                                                                                                                                                                       |
| `r2_buckets[].binding`            | `"LFS"`              | Git LFS file contents, keyed `lfs/<repository id>/<oid>`                                                                                                                                                                                                                                                                                                                                           |
| `r2_buckets[].binding`            | `"ACTIONS_LOGS"`     | Actions step logs, keyed `actions/<repository id>/<run>/<job>/<step>.log`                                                                                                                                                                                                                                                                                                                          |
| `r2_buckets[].binding`            | `"ACTIONS_CACHE"`    | The Actions cache (`actions/cache`, `setup-node`'s `cache:`): zstd tarballs keyed `actions-cache/<repository id>/<ref>/<key>.tar.zst`; and build artifacts (`upload-artifact`) under `actions-artifacts/`, kept as long as their run. | `workflows[].binding`             | `"ACTIONS_RUN"`      | One Workflow instance per Actions run (`class_name: "ActionsRun"`)                                                                                                                                                                                                                                                                                                                                 |
| `durable_objects.bindings[].name` | `"JOB_RUNNER"`       | One `JobRunner` Durable Object per Actions job; it owns the job's container                                                                                                                                                                                                                                                                                                                        |
| `durable_objects.bindings[].name` | `"ACTIONS_QUEUE"`    | One `ActionsQueue` Durable Object: the instance's queue of Actions jobs. Without it jobs start as soon as they're ready, with no limit                                                                                                                 |
| `durable_objects.bindings[].name` | `"MERGE_RESOLVER"`   | One `MergeResolver` Durable Object per AI conflict resolution: a Cloudflare Computer workspace and the pi agent                                                                                                                                                                                                                                                                                    |
| `durable_objects.bindings[].name` | `"AGENT_REVIEWER"`   | One `AgentReviewer` Durable Object per `engine: pi` review: the head commit checked out in a Cloudflare Computer workspace and a Pi agent with read-only tools. Without it, `engine: pi` agents review as a single pass and say so                                                                                                                                                                 |
| `durable_objects.bindings[].name` | `"LIVE"`             | One `LiveHub` Durable Object: the WebSocket hub that tells open pages to refresh (it relays pings and stores nothing). Without it pages still work, they just don't update live                                                                                                                                                                                                                    |
| `workflows[].binding`             | `"MERGE_RESOLUTION"` | AI conflict resolution and reviews: one instance per resolution attempt or reviewed commit, plus a sweep per push or merge (`class_name: "MergeResolutionWorkflow"`)                                                                                                                                                                                                                               |
| `ai.binding`                      | `"AI"`               | Workers AI: conflict resolution, reviewer agents' reviews, and Clef for `cloudforge/relevance@v1`, through AI Gateway (`AI_GATEWAY`)                                                                                                                                                                                                                                                               |
| `assets.binding`                  | `"ASSETS"`           | The built React app in `dist/client`                                                                                                                                                                                                                                                                                                                                                               |

`containers` defines the Actions runner: class `JobRunner` with `scheduling_policy: "durable_object"` and one image named `runner`, built from [`actions/runner/Dockerfile`](../actions/runner/Dockerfile) when you deploy (Docker must be running). Each job picks its instance size at start from `runs-on` (`ubuntu-latest` → `standard-2`, 1 vCPU, 6 GiB, 12 GB disk; `cloudforge-standard-1` … `cloudforge-standard-4` pick a size, up to Site admin → Settings → Actions → Largest runner (default `standard-4`; a workflow asking for more is invalid); `runs-on` may be an expression over the `github` and `matrix` contexts, so a workflow shared with GitHub can pick a CloudForge size only here). Jobs run on the image's preinstalled Node.js: `setup-node` doesn't download another version. To deploy without Actions, remove the `JobRunner` container, its Durable Object binding and export, the `ActionsQueue` Durable Object binding and export, the `ACTIONS_RUN` Workflow, and the `ACTIONS_LOGS` bucket. Without them, pushes never queue runs and the Actions tab says Actions isn't set up. To deploy without AI conflict resolution and reviews, remove the `MergeResolver` and `AgentReviewer` Durable Object bindings and exports and the `MERGE_RESOLUTION` Workflow: conflicts then have to be resolved locally, agents never review, and a person approves every pull request. To keep reviews but run every agent as a single pass, remove only the `AgentReviewer` binding and export.

Cache headers for the app come from [`public/_headers`](../public/_headers), which the build copies next to the built app: every path except `/assets/*` (the SPA's HTML, which names the current build's hashed script) is sent with `Cache-Control: no-store`, so Cloudflare's edge never serves a previous build's page after a deploy. Hashed files under `/assets/` are `public, max-age=31536000, immutable`. If you add a Cache Rule to the zone, leave HTML out of it or set it to respect origin headers.

The same file sets the app's security headers: a Content-Security-Policy (scripts only from the instance itself plus the theme boot script in `index.html`, allowed by its hash; images from anywhere over HTTPS, for README badges; no plugins, `<base>`, framing, or forms posting elsewhere), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`. A zone Transform Rule that adds scripts to pages (an analytics snippet, for example) needs its source added to `script-src`.

Keep `assets.run_worker_first` as shipped (it includes `/mcp` and `/.well-known/*`, which the MCP server and OAuth discovery need): the git endpoint (`/<owner>/<repo>.git/...`) and `/api/*` must reach the worker before static asset handling.

## Variables

Variables marked **Default only** are defaults: **Site admin → Settings** overrides them, stored in D1 (`instance_settings`), and takes effect without a deploy. They're read only where they're used (invitations, reviews, the MCP handshake, page loads), never on every request. Deploy-time facts (`BASE_URL`, the R2 account, and bucket names, which must match the bindings) stay here only.

Saving a setting or restoring its default requires the existing recent local authentication and current site-admin
authority at the actual D1 write. If that authority changes while the request waits, the response is `409` and no
successful settings audit is recorded; refresh and retry explicitly. Resetting a setting that already uses its
default still succeeds while the original authorization remains valid. A later audit storage failure does not
undo a completed setting change or ask the browser to repeat it. Unregistered setting keys return `404`.

### Usage & cost

Site admin → **Usage & cost** shows what this deployment uses on Cloudflare and what it would cost. CloudForge records Actions runner time, Workers AI calls, and emails itself. Everything else comes from Cloudflare's GraphQL Analytics API, which a daily cron (`triggers.crons`: `30 2 * * *`, 02:30 UTC) pulls into D1. Every query is filtered to the resources named below, so other things on the account never show up as CloudForge's. Leave a variable empty to skip that metric; it then shows as "not configured".

| Variable                         | Example                       | Purpose                                                                                                             |
| -------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `WORKER_NAME`                    | `cloudforge`                  | This Worker's script name (the top-level `name`), for Workers requests and CPU time                                 |
| `D1_DATABASE_ID`                 | `xxxxxxxx-xxxx-…`             | The `DB` database's `database_id`, for rows read and written and storage                                            |
| `ACTIONS_LOGS_BUCKET_NAME`       | `cloudforge-actions-logs`     | The `ACTIONS_LOGS` bucket's name. With `LFS_BUCKET_NAME` and `ACTIONS_CACHE_BUCKET_NAME`, the R2 buckets to measure |
| `ARTIFACTS_NAMESPACE`            | `cloudforge`                  | The `artifacts[].namespace`, for Artifacts operations                                                               |
| `ACTIONS_WORKFLOW_NAME`          | `cloudforge-actions-run`      | The `ACTIONS_RUN` Workflow's `name`                                                                                 |
| `MERGE_RESOLUTION_WORKFLOW_NAME` | `cloudforge-merge-resolution` | The `MERGE_RESOLUTION` Workflow's `name`                                                                            |
| `JOB_RUNNER_NAMESPACE_ID`        | `0123…cdef`                   | Durable Object namespace ID of `JobRunner`: `yarn cloudforge install` fills in all four after the first deploy      |
| `MERGE_RESOLVER_NAMESPACE_ID`    | `0123…cdef`                   | Same, for `MergeResolver`                                                                                           |
| `AGENT_REVIEWER_NAMESPACE_ID`    | `0123…cdef`                   | Same, for `AgentReviewer`                                                                                           |
| `LIVE_NAMESPACE_ID`              | `0123…cdef`                   | Same, for `LiveHub`                                                                                                 |

`R2_ACCOUNT_ID` is the account the queries read, and `AI_GATEWAY` names the gateway whose request count is shown (for the whole gateway, which other apps or a dev instance may share, so it is never added to CloudForge's totals).

The figures are estimates, not an invoice:

- Prices live in one table, [`worker/src/usage/pricing.ts`](../worker/src/usage/pricing.ts), with the date they were last checked and their sources. Costs are computed on read, so fixing a price re-prices history.
- Included allowances and the $5 plan fee are per Cloudflare account. The page shows CloudForge's usage at list price and the cost if CloudForge had the allowances to itself. If other things run on the account, the real bill for CloudForge's usage falls between the two.
- Containers: memory and disk are billed on the provisioned instance size, so runner time × size is exact. vCPU is billed on active use, so runner time × vCPUs is an upper bound. Workers AI is billed in neurons. The page prices recorded token counts at Cloudflare's per-model rates.
- Not measured: Artifacts storage, Workflows storage, container egress, and Workers Logs events, which have no analytics dataset. Some Durable Objects, Workers CPU, Artifacts, and AI Gateway cost fields are not in Cloudflare's docs yet. If Cloudflare rejects one, only that metric shows as unavailable, with the reason.
- The cron re-reads the last three days, since analytics settle late. It also fills in up to four older days each run, so a new install has the last 30 days (Cloudflare's retention) after about a week. **Sync now** re-reads today and the last three days.

## OIDC identity linking

OIDC first binds an external identity to an existing member. SSO login is a separate, explicitly published capability for existing active bindings; it never creates or merges accounts by email. The installer has no new OIDC flags and leaves the provider disabled. See [OIDC identity linking and SSO](oidc.md) for protocol, local MFA, recovery and validation boundaries.

| Setting              | Location                                                           | Default and purpose                                                                                                                                                              |
| -------------------- | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `OIDC_PROVIDER`      | Worker variable, including `env.dev.vars` when used in development | `""` leaves this deployment unconfigured; it does not retire an already published provider. Otherwise a JSON **string** containing the public fixed provider configuration below |
| `OIDC_CLIENT_SECRET` | Worker secret; local `.dev.vars`                                   | Empty while disabled; required when `OIDC_PROVIDER` is configured. Never place it in the JSON, Git or the browser                                                                |

For example, the variable value in `wrangler.jsonc` is a string, not an embedded object:

```json
{
  "OIDC_PROVIDER": "{\"id\":\"company\",\"name\":\"Company identity\",\"issuer\":\"https://identity.example/tenant\",\"clientId\":\"replace-with-client-id\",\"version\":1}"
}
```

The example is binding-only: optional `loginEnabled` defaults to false. Omitted and explicit false retain the pre-SSO configuration digest, so upgrading neither enables login nor silently invalidates the old binding publication. To enable SSO, set `loginEnabled: true` inside the public JSON, increase the registered provider's `version`, register the additional callback and explicitly preview/publish the login capability as an administrator. The public `loginCallbackUrl` is null while disabled. Non-boolean switch values are rejected.

`allowedOrigins` is optional: an array of at most eight additional HTTPS DNS origins for discovered endpoints. The issuer origin is already allowed. This permits origins rather than arbitrary redirects; private IP literals, local names and redirects are rejected. It does not provide DNS resolution pinning or complete DNS rebinding protection. Choose only origins controlled by the intended provider.

Register the exact GET linking callback `<BASE_URL>/api/auth/oidc/callback/company` with the IdP. Enabling login also requires `<BASE_URL>/api/auth/oidc-sign-in/callback/company`; the purposes cannot exchange their state. Public SSO requires HTTPS `BASE_URL`; only localhost and loopback development origins may use HTTP. The client must support authorization code + S256, `openid profile email`, `client_secret_basic`, and signed RS256 or ES256 ID tokens. Set the secret in `.dev.vars` locally, or use `yarn wrangler secret put OIDC_CLIENT_SECRET` for the intended production Worker; do not run secret or deployment commands against an unintended environment.

After separately authorized migration and deployment, a site administrator opens the OIDC provider panel in **Site admin → Settings**, previews the deployed public configuration and its login capability, checks it and confirms publication. Publication requires the original live browser session and local password plus any enabled factor verified within five minutes. Until the deployed configuration matches the published registry and global generation, members cannot start a link or login action. Login additionally requires both deployed and published login enablement.

The provider id permanently identifies its exact issuer. Changing issuer requires a new id. Any change to an already registered id, including secret rotation, allowed origins, name, client id or callback origin, requires a strictly higher `version` and fresh administrator publication. Switching away and back does not free the old id or version. The secret participates in an internal configuration digest but is never returned by these APIs. Global `configGeneration` fencing invalidates old previews and callbacks even if an old Worker or cache remains alive.

To reliably disable linking and login, a live local administrator must preview and confirm **publication of retirement** in the provider panel, using recent password and any enabled factor proof. The D1 trigger sets `enabled=false`, retires the digest, advances generation, cancels pending actions and removes affected SSO-source sessions. Confirmation triggers and request-time source checks also enforce current authority. Publishing a replacement configuration likewise invalidates old SSO sources; an administrator using such a session may need to sign in again after applying the change. Retirement does not require valid deployed JSON or a client secret. Clearing `OIDC_PROVIDER` alone leaves only the current deployment unconfigured; it does not revoke D1 authority, old configuration snapshots or already-issued SSO sessions.

Missing or invalid deployed configuration makes status safely report `ready=false`; it does not mean global retirement has been published. Administrators can still publish retirement, and members can inspect and revoke their bindings with recent local proof. Registry entries and identity tombstones remain. Re-enabling requires a higher version and fresh publication. Binding migrations are `0057`–`0059`; SSO actions, private session-source fields and issuance/source constraints use generated migrations `0060` and `0061`. Production migration and deployment require explicit authorization. Browsers without Web Locks retain password login and do not use SSO. This section documents configuration, not a deployment already performed.

The deployment/CI templates set `observability.logs.invocation_logs=false` and `observability.redact_query_string=true`, retaining redacted application logs while hardening platform URL logging. Cloudflare's [invocation logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/#invocation-logs) otherwise include the request URL; the [Workers API](https://developers.cloudflare.com/api/resources/workers/) describes query redaction. The test configuration disables invocation logs but omits query redaction because its embedded Wrangler schema does not support that field; test-runtime results do not establish deployed platform redaction. These defaults do not rewrite an operator's ignored configuration. External Logpush/Tail, native metadata and path-token exposure through metadata have not been checked in production; these defaults do not establish that every logging surface is secret-free.

## Environments

The top level of `wrangler.jsonc` is production (`yarn deploy`). The `env.dev` block is what `yarn dev` runs: a local D1 database, and Artifacts in a separate `cloudforge-dev` namespace (Artifacts has no local emulator), so development never touches production repositories. Likewise, dev LFS files go to a separate `cloudforge-lfs-dev` bucket (a real one, since pre-signed URLs must reach R2). Actions jobs in dev run in local Docker containers, so Docker must be running for `yarn dev`, and their logs go to a local R2 bucket.

## Cron Triggers

`triggers.crons` (`"17 4 * * *"`, daily) runs housekeeping: it deletes Actions runs that finished more than **Site admin → Settings → Keep Actions runs for** days ago (default 90, or keep forever), with their jobs, steps, and step logs in R2. Queued and running runs are never touched. Site admin shows when it last ran and how much it deleted.

`"*/5 * * * *"` (every five minutes) retries webhook deliveries that failed (see [Webhooks](webhooks.md)) and sends notification emails a request was cut off before. It does nothing when there is nothing due.
