# 团队与权限：现状与扩展

本文梳理这个分叉里“谁能看、谁能改”是怎么实现的，以及往哪些方向扩展、各要动多少代码。代码位置以仓库根目录为准。

## 一、现状

### 1. 站点角色：只有两级

- 账户由 better-auth 管理，`users.role` 只有 `admin`（站点管理员）和 `user`（成员，空值也当成员），另有 `banned` 标记。来源是 better-auth 的 `admin()` 插件（`worker/src/auth/index.ts`）。
- 站点管理员的特权集中在两处：
  - `requireAdmin` 中间件（`worker/src/auth/guards.ts`），在邀请、团队设置、站点管理、用量、设置检查、Agent 管理等处共挂载了 18 次（有的挂在整个路由组上）；
  - 仓库权限函数里“管理员对所有仓库读写管”（见下文）。
- 前端有十几处用 `role === 'admin'` 决定显示什么（侧栏的站点管理、新建菜单的邀请等），只影响界面，真正的拦截都在后端。
- 账户的来源有三种：初始设置创建的第一个管理员、管理员发出的邀请（邀请时可选 `admin` 或 `user`），以及本分叉新增的自助注册（只能注册成 `user`）。

### 2. 团队：一个实例只有一个，而且没有成员名单

- `teams` 表（`worker/src/db/app.schema.ts`）在设计上只放一行。`PUT /api/team`（只有管理员能调）负责创建或改名，团队的 slug 与用户名共用 URL 命名空间。
- **团队没有成员表**，所有成员都视为团队的一员。团队仓库（`repositories.team_id` 非空）的规则是：
  - 所有成员都能读（可见性只能是 internal 或 public，不能是 private）；
  - 创建者（记录在 `owner_id`）是该仓库的管理者；
  - 其他成员要写，仍然得被加为协作者。
- 也就是说，“团队”目前只是一个共享的命名空间（`/acme/仓库名`），并不是一个权限单位。

### 3. 仓库权限：一个函数说了算

核心在 `worker/src/lib/repos.ts`：

| 身份                     | 读                          | 写（推送、合并） | 管理（设置、删除、协作者） |
| ------------------------ | --------------------------- | ---------------- | -------------------------- |
| 站点管理员               | 全部仓库                    | ✓                | ✓                          |
| 所有者 / 团队仓库创建者  | ✓                           | ✓                | ✓                          |
| 协作者                   | ✓                           | ✓                | ✗                          |
| 其他成员                 | team、internal、public 仓库 | ✗                | ✗                          |
| 未登录访客（本分叉新增） | 只有 public 仓库            | ✗                | ✗                          |

- `permissionsFor` / `permissionsForMany` 计算单个仓库的读、写、管三种权限；`visibleTo` 是列表用的 SQL 过滤条件，两者必须保持一致（代码注释里也强调了这一点）。
- 每个仓库接口都经过 `loadRepo` 中间件：读不到就返回 404（不暴露仓库是否存在），写和管由各接口再检查 `perms.write` / `perms.admin`。
- git 推拉（`worker/src/git-http.ts`）和 LFS（`worker/src/lfs-http.ts`）用个人访问令牌认证，复用同一套 `permissionsFor`。
- 协作者表 `repository_collaborators` 只有（仓库, 用户）两列，**没有权限等级**：协作者一律可读可写。

### 4. 其他与权限相关的机制

- **评审 Agent**：每个 Agent 是一个不能登录、不能有密码的用户（认证钩子里有专门拦截）。它们按仓库被邀请（`repository_agents`）。“受保护（guarded）”的 Agent（如安全、数据类）提出的评审意见必须由有推送权限的人逐条批准。
- **MCP 审核者应用**：用户可以把某个 MCP 应用标为“审核者”，让它代表自己批准评审意见（`mcp_moderators`）。
- **受保护分支**（`repositories.protected_branches`）：只表示“CloudForge 不会自动变基这些分支”，**不是**推送权限控制，有写权限的人照样能推送。

### 5. 已经具备、但没有界面的能力

- better-auth 的管理员接口已经启用：`/api/auth/admin/set-role`（改角色）、`ban-user` / `unban-user`（封禁）、`remove-user`（删除）、`impersonate-user`（模拟登录）等。站点管理员可以直接调这些接口，但站点管理页上没有对应的按钮（页面上写着“这里不能移除成员，也不能修改角色”）。
- **删除用户有风险**：`repositories.owner_id` 设置了 `ON DELETE CASCADE`，删掉一个用户会连带删掉他拥有的所有个人仓库，**以及他创建的团队仓库**。封禁不会删除数据，是更安全的选择。

## 二、扩展方向（按投入从小到大）

### A. 成员管理界面：改角色、封禁 / 解封（小，约半天到一天）

- 后端几乎现成：直接用 better-auth 的 admin 接口。需要加两道保护：
  - 不能降级或封禁最后一个站点管理员；
  - 不能对 Agent 操作（认证钩子里已经拦了）。
    另外每次操作要记审计日志。
- 前端：在站点管理的成员列表里，每行加“设为管理员 / 设为成员”和“封禁 / 解封”。
- **删除成员**建议先不做，或者做成“先把他的仓库转给别人，再删除”，否则会连带删掉仓库。

### B. 协作者分级：只读 / 读写 / 管理（中，约一到两天）

- 给 `repository_collaborators` 加一个 `role` 列（`read` | `write` | `admin`），用 drizzle 生成迁移。现有行默认是 `write`，行为不变。
- 修改 `permissionsOf`：按 `role` 给读、写、管三种权限。`visibleTo` 不用改，因为协作者本来就能看到仓库。
- 前端：在仓库设置的协作者列表里加一个下拉框。
- 解决的问题：私有仓库可以只给某人只读权限；也可以设“副管理员”，不必事事找所有者。

### C. 分支推送保护（中，约两天）

- 在 `git-http.ts` 处理 receive-pack（推送）请求时，先读出请求体开头的 ref 更新指令（pkt-line 格式），对匹配受保护规则的分支，只允许仓库管理员推送，或者禁止强制推送和删除分支。
- 合并接口（`landPull`）里加同样的判断。
- 可以复用现有的 `protected_branches` 匹配规则，再加一个“谁能推送”的设置。

### D. 多团队 + 团队成员与角色（大，约一到两周）

- `teams` 表允许多行，新增 `team_members(team_id, user_id, role: member | maintainer)`。
- 团队仓库的权限改为：团队成员可写（或只读），维护者可管理。`permissionsOf` 和 `visibleTo` 要同步改，团队仓库也可以支持“仅团队可见”。
- 影响面：命名空间（`worker/src/lib/namespaces.ts`）、新建仓库时选择归属团队、团队页面、搜索、MCP 工具、Agent 的统计与可见性（它们都调用了 `visibleTo`），测试要覆盖每一处读权限。
- 这一步完成后，才能像 GitHub 那样“把某个团队授权到某个仓库”。

### E. 细粒度站点角色（中到大）

- 例如“审计员”（能看审计日志、用量，但不能改设置）、“成员管理员”（只能邀请和封禁）。
- better-auth 的 admin 插件支持自定义角色和权限（`createAccessControl`）。需要把 `requireAdmin` 拆成按权限检查（如 `requirePermission('audit:read')`），并逐个梳理这 18 处挂载点和前端的 `role === 'admin'` 判断。

## 三、建议

1. **先做 A**：投入小、收益直接，而且开放自助注册以后，封禁能力尤其重要。
2. **再做 B**：私有仓库的只读授权是最常见的缺口。
3. **C、D、E 看团队规模再定**：D 改动面最大，建议单独开一个分支，先补充权限相关的测试再动手。

所有权限改动都要保持“仓库权限只在 `repos.ts` 一处计算”的原则，读规则改动时 `permissionsOf` 和 `visibleTo` 一起改，并在 `worker/src/__tests__/` 里补上对应的测试（可参考 `teams-visibility.test.ts` 和 `public-repos.test.ts`）。
