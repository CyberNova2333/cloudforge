# 身份认证与账户恢复

本设计对应路线图第二阶段。第一步实现成员自愿启用的 TOTP 验证器与一次性恢复码；强制全员 MFA、OIDC SSO 和通行密钥按下面的边界分别推进。

## 第一版的认证边界

CloudForge 仍是单租户实例。人的网页身份来自 better-auth 的 D1 会话，Git/LFS 的个人访问令牌、仓库部署令牌及 MCP OAuth 凭据分别验证。代理账号不能取得人的会话或认证因子。

| 入口                               | 第一版行为                                                                                                        |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 用户名或邮箱 + 密码                | 未启用 TOTP 时维持原流程；已启用时必须再完成 TOTP 或恢复码挑战，之后才允许访问账户和完成 OAuth 授权               |
| 账户设置 → 安全                    | 输入当前密码生成待验证的 TOTP；首次验证码确认后启用；显示一次恢复码                                               |
| 更换恢复码、关闭 TOTP              | 当前密码与最近完成的第二因子验证共同授权；证明绑定当前会话、有时限、只供一次敏感操作                              |
| 现有网页会话                       | 启用时撤销旧会话，保留经过确认的新会话；普通请求仍实时检查 D1 会话及当前封禁状态                                  |
| 邮箱验证、密码重置、管理员模拟登录 | 不能替已启用的账户完成第二因子；密码重置不能删除 TOTP 或恢复码                                                    |
| 已发行 PAT、仓库部署令牌           | 继续按原权限、期限和撤销规则运行                                                                                  |
| 已发行 MCP OAuth 凭据              | 撤销网页会话只将绑定的 sessionId 置空，已有 JWT 和刷新令牌继续按当前 consent/封禁规则验证；主动断开应用会立即撤权 |
| 新 MCP 授权                        | 网页登录先完成第二因子，再继续原签名 OAuth 请求、同意页及 PKCE 流程                                               |

TOTP 使用已有 better-auth 插件的算法和加密，不增加发往外部服务的验证码或二维码请求。不提供短信、邮件验证码、记住设备或免验证启用。服务端拒绝这些未开放的调用方式，不能靠隐藏网页按钮限制。

登录挑战十分钟过期，每个挑战最多五次失败；账户级锁定覆盖重复登录及已登录会话的敏感操作验证，跨 IP 不能绕过。已登录验证先在 D1 原子预留尝试，累计十次失败锁定十五分钟，成功验证清零。TOTP 的同一时间步只能成功使用一次；刚登录或刚启用后若立即修改设置，应等待验证器显示下一枚验证码。

TOTP 秘密和恢复码只在当前页面内存中呈现，不写入 URL、浏览器持久存储、查询缓存或日志。认证接口返回 `Cache-Control: no-store`。数据库中 TOTP 秘密加密；恢复码按插件的安全存储方式保存。服务端限制猜测次数，并通过 D1 原子写入防止验证码、恢复码和登录挑战的并发重复使用。D1 的多条依赖写入使用 `batch()` 的事务保证，不假定其支持跨请求交互式事务。

授权变更写入实例审计日志，只含操作者、操作类型和必要标识；不得写入密码、TOTP 秘密、验证码、恢复码或完整 OAuth 请求。第一版尚不声称所有现有机器凭据均携带 MFA 强度。

## 成员的启用和恢复流程

1. 从账户设置进入“安全”，输入当前密码，将密钥导入自己的验证器。
2. 输入验证器生成的验证码确认启用。取消或离开未完成的设置不能把账户标成已启用。
3. 将一次性恢复码保存在账户之外的安全位置。每个码只可使用一次；重新生成整组后，旧码立即失效。
4. 登录时可在验证器验证码与恢复码之间切换。密码错误、挑战失效或过期时重新登录；浏览器刷新不会把未完成的挑战当作已登录。
5. 丢失验证器但还有恢复码时，用恢复码登录，再以密码和第二因子验证关闭原因子后重新绑定。应预留另一枚恢复码用于这个敏感操作。

忘记密码与丢失第二因子是两件不同的事。邮件重置、管理员发送的重置链接及 `cloudforge reset-password` 只处理密码，不会解除第二因子；更换密码会撤销基于旧密码建立的未完成双因素挑战。管理员应先保存恢复码，再启用 TOTP；建议至少保留两名有独立因子的管理员。

网页登录挑战绑定实际验证过的密码和因子版本，账户状态变化后不能凭旧挑战重建会话。成员在当前会话修改密码时保留该会话并撤销其他浏览器会话；邮件重置、管理员为其他成员设置密码及 CLI 重置撤销该成员的全部浏览器会话。

备份和迁移实例时应保留 `BETTER_AUTH_SECRET` 的独立安全备份。它同时保护数据库中的验证器秘密和恢复码；单独替换该密钥不能恢复账户，反而会使已有加密材料无法解密。不要把密钥轮换当作丢失验证器的恢复方式。

同时丢失验证器和所有恢复码时，使用下面的独立离线恢复命令。没有网页管理员代解除入口，也不把邮箱或现有机器令牌当作替代因子。恢复不能隐含在密码重置中；本设计不授权运行生产恢复、迁移或部署。

## 独立离线因子恢复

`cloudforge reset-mfa` 通过 Cloudflare 管理凭据直接访问明确指定的 D1。它不依赖可用的网页登录，适用于最后一位管理员失去全部第二因子的情况。应先独立核实申请人的身份及恢复原因，再运行命令。读取预览不证明令牌具有写权限；实际写入仍由 Cloudflare 校验 D1 写权限。

从源码检出目录操作已记录实例：

```bash
yarn cloudforge reset-mfa octocat --name cloudforge --reason "验证器与全部恢复码遗失" --plan
yarn cloudforge reset-mfa octocat --name cloudforge --reason "验证器与全部恢复码遗失"
```

手动部署的实例必须同时明确账户和数据库；不能自动选中唯一账户或唯一安装。包安装方式将 `yarn cloudforge` 替换为已安装版本的 `npx @cybernova2333/cloudforge`。

```bash
yarn cloudforge reset-mfa octocat --account ACCOUNT_ID --database DATABASE_ID --reason "验证器与全部恢复码遗失" --plan
```

预览展示账户、数据库名称与 UUID、安装标记、成员 ID、用户名/邮箱及撤销范围。终端确认默认拒绝；非交互执行必须提供 `--yes --expect-plan <预览摘要>`。目标身份、密码、因子秘密或安装标记在预览后变化会使执行失败，需要重新预览确认。恢复原因写入审计，因此不得填写密码、验证码或其他秘密。

恢复同时撤销 TOTP 秘密、整组恢复码、该成员的全部浏览器会话及会话内第二因子证明、未完成的第二因子挑战及其尝试计数、历史受信设备记录；密码保持不变，之后可凭密码登录并重新绑定。封禁和角色保持不变，代理账户及已封禁成员不接受恢复。未完成的待绑定因子也可清除。PAT、仓库部署令牌与既有 MCP consent/刷新凭据保留，删除网页会话只将其 sessionId 置空；若怀疑凭据泄漏，应另行撤销这些机器凭据。

执行只有一条受目标快照约束的 `INSERT … SELECT`，专用数据库触发器在同一 SQL 语句内完成撤销和 `user.mfa_reset` 系统审计；任一步失败会回滚整条语句。不会依赖 REST 多语句批次的未明确回滚语义，也不部署临时 Worker。数据库缺少对应迁移或触发器定义不匹配时拒绝执行。响应丢失时不自动重试写入，通过公开的恢复事件 ID 只读核验结果；无法确认时必须先核验，不能把未知结果当作未执行。

旧因子验证、旧敏感修改和旧会话密码轮换有凭据/因子代际及会话检查，不能在恢复后重建有效的第二因子会话。密码保持有效，因此不承诺中止所有恢复前开始的密码登录：在恢复后完成的密码认证可能按此时无因子的账户状态登录。统一认证版本与强制策略属于后续工作。

## 后续强制策略

站点管理员强制全员启用前，需要单独实现以下机制，不能仅检查 `users.twoFactorEnabled`：

- 每个会话记录实际认证方法、完成时间、策略版本及第二因子强度。旧会话被新策略失效化；尚未注册因子的成员只能进入有限的绑定与退出流程。
- 因子变更、敏感凭据创建、账户关联和管理员操作要求最近验证。改变策略、封禁、撤权以及紧急恢复及时影响会话和授权。
- 明确已有 MCP consent/access token/refresh token 的迁移规则。JWT 不天然知道后来的策略变化，必须结合实时授权版本校验或撤销同意记录；仅撤销网页会话不够。
- PAT 和部署令牌仍是自动化凭据，不交互式输入验证码。分别定义创建时的最近验证、到期迁移、管理员豁免、审计与撤销；先预览影响再执行策略，避免无提示中断部署。
- 最后一位管理员的恢复方式、独立离线授权、恢复审计和失效化必须先通过测试，再允许启用强制策略。

## 后续 OIDC SSO 与通行密钥

OIDC 优先只允许已有成员在已认证且最近验证的会话中显式关联。默认不自动注册，不凭同邮箱自动合并账户；将 issuer、subject 与本地身份唯一绑定，并检查签名、audience、state、nonce、PKCE 和回调地址。外部 `email_verified` 必须按受信任提供商的语义判断，不能复用当前“邀请/管理员创建账户视为已确认”的规则。

管理员配置的 provider 属于实例策略，需明确版本和失效机制；当前 `authFor` 按 env 缓存认证实例，直接更新 D1 设置不会刷新插件。新增提供商包前重新检查版本、CVE 和 D1 适配器事务语义。

SSO、社交登录、通行密钥等入口不会自动继承 twoFactor 对密码登录的挑战。接入时必须建立统一认证强度判断。通行密钥需要固定 RP ID、可信 origin、明确 `userVerification` 要求及恢复边界；不能将默认 `preferred` 等同于完成强制 MFA。

## 依据与验证

实现以锁定的 better-auth 1.7.7 源码为准，并核对 [twoFactor 官方文档](https://better-auth.com/docs/plugins/2fa)、[账户关联规则](https://better-auth.com/docs/concepts/users-accounts)、[generic OAuth](https://better-auth.com/docs/plugins/generic-oauth) 和 [Cloudflare D1 batch 事务语义](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)。

必须覆盖真实 D1 上的启用确认、错误与过期挑战、并发恢复码消费、TOTP 重放、跨会话证明、密码重置后的因子保留、邮箱验证与模拟登录绕过、OAuth 登录续接、CSRF、秘密响应缓存及审计脱敏。依赖审计只表示当时的已知公告结果，不能代替这些集成检查。
